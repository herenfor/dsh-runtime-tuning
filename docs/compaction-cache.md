# 压缩缓存：验证记录

实验日期：2026-11-15；发布准备复核：2026-11-16。

## 结论

当主对话使用 `max`，官方摘要省略推理档位而回落 `high` 时，本次服务端实验出现缓存失配。修复让同模型摘要沿用有效档位；独立摘要模型与不支持的档位按配置和能力处理。两组使用相同的历史输入，费用变化来自非缓存输入与缓存输入的比例。

实测版本和平台集中见 [README](../README.md#已测版本)。下列结果来自发布前源码的合成会话对照。

## 实际插件对照

直接通过 `ctx.plugin` 挂载本插件默认导出，官方组使用原 `BasicCompactionEngine`。使用相同合成会话种子、system、工具定义、模型和摘要上限，最终请求体除 `output_config.effort` 外一致；先原样重复主请求确认缓存已建立。

**本组摘要费用等价额减少 70.70%。** 统计对象为两次摘要请求，计算包含各自的实际输入和输出。

费用按实验日期公开 Flash 闲时 API 价计算：非缓存输入 $0.15/M、缓存输入 $0.003/M、输出 $0.6/M。实验使用账户授权路由，金额为服务端 token 用量的公开 API 价格等价额。[官方价格](https://api-docs.deepseek.com/quick_start/pricing/)

## 服务端计量与验收

本轮共 7 次真实调用（2 次主请求预热、2 次摘要、3 次续接/重复），全部正常结束。每次将服务端最终 SSE usage 的 input/cache-read/cache-write/output 四项与适配器逐项核对，两次摘要均有完整 start/summary/end，且保留官方 8 节结构。

复测脚本的一次重复续接把端口返回为字符串而非数字，触发了过严的类型断言；提问未要求字段类型，事实仍正确。随后仅补跑剩余对照，没有重复已完成请求。该组不作为严格 JSON Schema 验收。

此前另有两轮共 20 次请求形态探索，以及 24 次官方入口验证。后者覆盖手动与自动压力压缩，交换对照顺序，5 次摘要完整结束，5 次不提供答案的续接均恢复 6 项关键决策。自动形态在 effort 对齐后达到 97.53% 缓存命中；这组自动真实请求由研究脚本构造并注入对齐参数。当前插件的自动压力、溢出、模型切换和并发隔离另有实际宿主本地集成测试。

## 测试环境与计量口径

- 数据为虚构项目文本，工具部分使用固定 schema；模型请求名为 `deepseek-flash`。
- 官方 Session、TokenMeter、压缩引擎和 Adapter 为实际宿主模块；维护 owner 与文件 flush 由研究脚本提供。JSONL 恢复及旧会话升级通过本地宿主回归验证。
- 缓存对照在主请求原样重复并确认预热后进行，每组使用相同前缀与路由。
- 摘要替换旧历史后，续接使用新前缀建立和复用缓存；本文的费用对照统计摘要生成阶段。[官方缓存机制](https://api-docs.deepseek.com/guides/kv_cache/)
- `input_tokens` 不含缓存命中，应使用最终 `message_delta.usage`，不能与初始值重复相加。[官方计量说明](https://api-docs.deepseek.com/guides/anthropic_api/#streaming-and-token-usage)

验证用的原始会话、凭据读取配置和个人协作记录不随包分发。
